Kubernetes და RKE2შუალედურის კონსპექტი და ქვიზები

ხუთი მასალა ერთ გვერდზე: ორი ლექცია Kubernetes-ზე, RKE2-ის გზამკვლევი AWS EC2-ზე, Quiz 2-ის პრაქტიკული დავალება და სანიმუშო თეორიული ქვიზი. ★ ქვიზი ნიშნავს, რომ კითხვა სანიმუშო ქვიზიდანაა სიტყვასიტყვით.

1Kubernetes-ის საფუძვლები

Kubernetes (K8s) კონტეინერიზებული აპლიკაციების (workload-ების) მართვის პლატფორმაა. ის ორკესტრირებს გამოთვლით რესურსს, ქსელს და საცავს, ამიტომ აპლიკაცია ერთნაირად მუშაობს სხვადასხვა ინფრასტრუქტურაზე. დაწერილია Go ენაზე.

კლასტერი node-ების ერთობლიობაა, რომლებიც კონტეინერიზებულ აპლიკაციებს უშვებენ და ერთ სისტემად იმართება. Node შეიძლება იყოს ფიზიკური სერვერი ან ვირტუალური მანქანა, cloud-ში ან on-premises. მარტივ კლასტერში ერთი control-plane (master) და რამდენიმე worker node-ია; production-ში control plane რამდენიმე მანქანაზე ეშვება.

კონტეინერი და image

  • კონტეინერი — აპლიკაცია დამოკიდებულებებით, იზოლირებული, მაგრამ ჰოსტის OS kernel-ს იზიარებს. ამიტომ VM-ზე მსუბუქია.
  • განმეორებადობა — ყველა დამოკიდებულება შიგნითაა, ამიტომ კონტეინერი ყველგან ერთნაირად იქცევა.
  • Container image — გასაშვებად მზა პაკეტი: კოდი, runtime, ბიბლიოთეკები, ნაგულისხმევი პარამეტრები.
  • Immutability — გაშვებულ კონტეინერში კოდს არ ცვლი: ააწყე ახალი image და კონტეინერი თავიდან შექმენი.
  • Container runtime — კონტეინერებს რეალურად უშვებს: containerd, CRI-O ან CRI-ს სხვა იმპლემენტაცია. RKE2 იყენებს containerd-ს; Docker მხოლოდ image-ის ასაწყობ მანქანაზეა საჭირო.

kubectl და kubeconfig

kubectl ბრძანების ხაზის ინსტრუმენტია, რომელიც control plane-ს Kubernetes API-ით ესაუბრება. მისით ქმნი, ნახულობ, ცვლი და შლი რესურსებს და აკეთებ troubleshooting-ს.

კონფიგურაციას (kubeconfig) ნაგულისხმევად ეძებს $HOME/.kube/config-ში; სხვა ფაილს უთითებ KUBECONFIG ცვლადით ან --kubeconfig ფლაგით. RKE2-ში ადმინის kubeconfig არის /etc/rancher/rke2/rke2.yaml — მასში ადმინის credentials-ია, არასდროს აქვეყნებ.

Namespace

Namespace კლასტერის ლოგიკური დაყოფაა: რესურსები ჯგუფდება და სისტემურისგან გამოიყოფა. მაგ. demo ან quiz2 აპლიკაციისთვის, kube-system სისტემური კომპონენტებისთვის. ბრძანებაში: -n <name>, ყველასთვის — -A.

2კლასტერის არქიტექტურა

Control Plane იღებს გადაწყვეტილებებს, Worker Node-ები კი Pod-ებს რეალურად უშვებენ. ყველა კომპონენტი ერთმანეთს მხოლოდ kube-apiserver-ის გავლით ესაუბრება.

Control Plane-ის კომპონენტები

კომპონენტირას აკეთებსდასამახსოვრებელი
kube-apiserverავლენს Kubernetes API-ს; control plane-ის front endჰორიზონტალურად სკალირდება: მეტი ინსტანსი + load balancing
etcdconsistent, highly-available key-value საცავი კლასტერის ყველა მონაცემისთვისbackup: ჩაშენებული snapshot ან volume snapshot; snapshot დაშიფრე
kube-schedulernode-ის გარეშე ახლად შექმნილ Pod-ს node-ს ურჩევსითვალისწინებს რესურსებს, policy-ებს, affinity/anti-affinity-ს, data locality-ს, deadlines
kube-controller-managercontroller პროცესებს (control loop-ებს) უშვებსყველა controller ერთ binary-ში, ერთ პროცესადაა
  • Node controller — node-ის გათიშვას ამჩნევს და რეაგირებს.
  • Job controller — Job ობიექტებისთვის (ერთჯერადი ამოცანები) ქმნის Pod-ებს და ბოლომდე ასრულებს.
  • Endpoints controller — ავსებს Endpoints ობიექტს, ანუ Service-ებს Pod-ებთან აკავშირებს.
  • Service Account & Token controllers — ახალ namespace-ებში ქმნიან ნაგულისხმევ ანგარიშებს და API ტოკენებს.

Control plane-ის კომპონენტები ნებისმიერ მანქანაზე შეიძლება გაეშვას, მაგრამ setup სკრიპტები მათ ჩვეულებრივ ერთ მანქანაზე უშვებენ და იქ მომხმარებლის კონტეინერებს არ ათავსებენ. Production-ში control plane რამდენიმე მანქანაზეა (HA).

Worker Node-ის კომპონენტები

კომპონენტირას აკეთებს
kubeletაგენტი ყოველ node-ზე: იღებს PodSpec-ებს და ზრუნავს, რომ კონტეინერები გაშვებული და ჯანსაღი იყოს. Kubernetes-ის გარეშე შექმნილ კონტეინერებს არ მართავს.
kube-proxyქსელური proxy ყოველ node-ზე, Service-ის კონცეფციის ნაწილი. ინახავს ქსელურ წესებს; იყენებს OS-ის packet filtering-ს, თუ არის, თუ არა — ტრაფიკს თავად აგზავნის.
container runtimeimage-ს registry-დან იწერს, ხსნის და აპლიკაციას უშვებს (containerd, CRI-O).

Node worker მანქანაა (ვირტუალური ან ფიზიკური), რომელსაც control plane მართავს. ერთ node-ზე ბევრი Pod შეიძლება იყოს; ავტომატური დაგეგმვა თითო node-ის თავისუფალ რესურსს ითვალისწინებს.

3Workload ობიექტები

Pod

Pod Kubernetes-ის უმცირესი განლაგებადი (atomic) ერთეულია: ერთი ან მეტი კონტეინერი და მათი საერთო რესურსები — Volumes (საცავი), ერთი უნიკალური კლასტერული IP და საერთო port space, გაშვების ინფორმაცია (image-ის ვერსია, პორტები).

Pod აპლიკაციის „ლოგიკური ჰოსტია“: მისი კონტეინერები ყოველთვის ერთ node-ზეა, ერთად იგეგმება და ერთმანეთს localhost-ით ხედავს. node-ის გაფუჭებისას იდენტური Pod-ები სხვა node-ებზე იქმნება.

Pod-ები დროებითია: ახალ Pod-ს ახალი სახელი და IP აქვს. ამიტომ Pod-ს პირდაპირ იშვიათად ქმნიან — ამას Deployment-ს ან StatefulSet-ს ანდობენ.

Deployment და ReplicaSet

Deployment Pod-ებისა და ReplicaSet-ების დეკლარაციულ განახლებას უზრუნველყოფს: აღწერ სასურველ მდგომარეობას, Deployment controller კი რეალურს მას კონტროლირებადი ტემპით უახლოებს.

ReplicaSet უზრუნველყოფს, რომ Pod-ის ზუსტად N ასლი იყოს გაშვებული. იერარქია: Deployment → ReplicaSet → Pods. Deployment ყოველი ახალი Pod template-ისთვის ახალ ReplicaSet-ს ქმნის, რაც rolling update-ს და rollback-ს შესაძლებელს ხდის.

  • metadata.name — Deployment-ის სახელი (მაგ. nginx-deployment)
  • spec.replicas — Pod-ების სასურველი რაოდენობა (მაგ. 3)
  • spec.selector.matchLabels — როგორ პოულობს Deployment თავის Pod-ებს
  • spec.template.metadata.labels — Pod-ის label-ები; selector-ს უნდა ემთხვეოდეს
  • spec.template.spec.containers — სახელი, image (მაგ. nginx:1.14.2), containerPort

kubectl get deployments სვეტები: READY (მზა/სასურველი, მაგ. 3/3), UP-TO-DATE (უახლეს template-ზე განახლებული), AVAILABLE (ხელმისაწვდომი), AGE.

Scaling და self-healing

  • Scaling: kubectl scale deployment nginx --replicas=4 -n demo ცვლის სასურველ რაოდენობას.
  • Self-healing: Deployment-ის Pod-ს თუ წაშლი, ReplicaSet შეამჩნევს დანაკლისს და ახალ Pod-ს შექმნის ახალი სახელით და IP-ით. სამუდამოდ მოსაშორებლად Deployment უნდა წაშალო ან replica-ები შეამცირო.
  • Rollout: kubectl rollout status deployment/<name> აჩვენებს განახლების მიმდინარეობას.

StatefulSet

StatefulSet stateful აპლიკაციებისთვისაა (ბაზები). Pod-ებს სტაბილური იდენტობა აქვს: სახელი რიგითი ნომრით (quiz2-stateful-app-0), რომელიც თავიდან შექმნისას იგივე რჩება.

  • თითო Pod-ს საკუთარი PVC აქვს volumeClaimTemplates-იდან: <template>-<statefulset>-<ordinal>, მაგ. quiz2-data-quiz2-stateful-app-0.
  • სტაბილური ქსელური სახელისთვის საჭიროა Headless Service (clusterIP: None), რომელსაც serviceName ველით მიუთითებ.
  • Pod-ის წაშლისას იგივე სახელის Pod იქმნება და იგივე PVC-ს უერთდება — მონაცემი რჩება.

4ქსელი: Service და Ingress

Pod-ები დროებითია და ყოველ ახალ Pod-ს ახალი IP აქვს, ამიტომ „frontend“ Pod-ები „backend“ Pod-ებს IP-ით სანდოდ ვერ მიმართავენ. Service Pod-ების ჯგუფს აძლევს სტაბილურ IP-ს და DNS სახელს და მათ შორის ტრაფიკს ანაწილებს. Pod-ებს label selector-ით პოულობს; მზა Pod-ების მისამართები Endpoints / EndpointSlices-ში ინახება.

Service-ის ტიპები

ტიპისაიდან ხელმისაწვდომიმთავარი თვისება
ClusterIP (ნაგულისხმევი)მხოლოდ კლასტერის შიგნიდანვირტუალური IP, მარშრუტიზდება მხოლოდ კლასტერის ქსელში
NodePortგარედან: <NodeIP>:<NodePort>ყველა node-ზე ხსნის პორტს 30000–32767-დან (მაგ. 30082); ClusterIP-საც მოიცავს
LoadBalancerგარედან, cloud LB-ითგარე load balancer; AWS-ზე სჭირდება cloud controller ინტეგრაცია
ExternalName—Service-ის სახელს გარე DNS სახელზე მიამართავს (CNAME)
Headless (clusterIP: None)კლასტერის შიგნითვირტუალური IP არ აქვს; DNS Pod-ების IP-ებს აბრუნებს. StatefulSet-ისთვის

პორტები: port — Service-ის პორტი; targetPort — კონტეინერის პორტი; nodePort — node-ის პორტი (NodePort/LoadBalancer).

kubectl expose არსებულ Deployment-ს, ReplicaSet-ს, Pod-ს ან RC-ს ახალ Service-ად აქვეყნებს მისი selector-ით: kubectl expose deployment nginx --type=NodePort --port=80 --target-port=80 -n demo. --type-ის გარეშე იქმნება ClusterIP.

Ingress

Ingress API ობიექტია, რომელიც გარედან HTTP და HTTPS მარშრუტებს კლასტერის Service-ებამდე მიიყვანს. წესები (rules): host (მაგ. quiz2.example.test) და path (მაგ. /) → backend Service:port.

  • შესაძლებლობები: გარედან ხელმისაწვდომი URL-ები, load balancing, SSL/TLS termination, name-based virtual hosting.
  • Ingress Controller აუცილებელია — ის ასრულებს წესებს. მის გარეშე Ingress არაფერს აკეთებს.
  • ingressClassName ირჩევს კონტროლერს; არსებულ კლასებს აჩვენებს kubectl get ingressclass.
  • Ingress არ აქვეყნებს ნებისმიერ პორტს ან პროტოკოლს; სხვა პროტოკოლებისთვის NodePort ან LoadBalancer.
  • Default backend იღებს მოთხოვნებს, რომლებსაც არცერთი წესი არ ემთხვევა.

მარშრუტი: client → Ingress-managed load balancer → Ingress → routing rule → Service → Pods. ლოკალური ტესტისთვის hosts ფაილში: <WORKER_PUBLIC_IP> quiz2.example.test.

  • Edge router — კლასტერის firewall პოლიტიკას ახორციელებს (cloud gateway ან ფიზიკური მოწყობილობა).
  • Cluster network — ლოგიკური ან ფიზიკური კავშირები კლასტერის შიგნით კომუნიკაციისთვის.

kubectl port-forward

kubectl port-forward -n demo svc/nginx 8080:80 ლოკალურ 8080-ს Service-ის 80-ზე გადაამისამართებს. ნაგულისხმევად მხოლოდ 127.0.0.1-ზე ისმენს, ამიტომ საჯარო პორტის გახსნა არ სჭირდება. შემოწმება მეორე ტერმინალში: curl http://127.0.0.1:8080.

5Secret და Health Probes

Secret

Secret ინახავს პაროლს, ტოკენს, გასაღებს, რომ ისინი Deployment-ის YAML-ში ღიად არ ეწეროს.

  • Opaque — ზოგადი ტიპი ნებისმიერი key/value წყვილისთვის (APP_USERNAME, APP_PASSWORD).
  • მნიშვნელობები base64-ითაა კოდირებული — ეს დაშიფვრა არ არის. Secret-ები etcd-ში ინახება; საჭიროა encryption at rest და RBAC.
  • შექმნა: kubectl create secret generic quiz2-web-secret --from-literal=APP_USERNAME=quiz2user --from-literal=APP_PASSWORD=<value> -n quiz2
  • გადაცემა: env[].valueFrom.secretKeyRef (ერთი key), envFrom.secretRef (ყველა) ან volume.
env:
- name: APP_PASSWORD
  valueFrom:
    secretKeyRef:
      name: quiz2-web-secret
      key: APP_PASSWORD

მითითების ჩვენება პაროლის გარეშე: kubectl describe deployment quiz2-web -n quiz2 — Environment-ში ჩანს <set to the key 'APP_PASSWORD' in secret 'quiz2-web-secret'>.

სამი Health Probe

Probe-ებს kubelet ასრულებს: პერიოდულად ამოწმებს კონტეინერს (HTTP GET, TCP ან exec) და შედეგის მიხედვით კონტეინერს ან Service-ის ტრაფიკს მართავს.

Probeრას ამოწმებსჩავარდნის შედეგი
Startupჩაირთო თუ არა აპლიკაციასანამ არ გაივლის, readiness და liveness გამორთულია. failureThreshold × periodSeconds (12 × 5 = 60 წმ) ამოწურვისას kubelet კონტეინერს კლავს და restartPolicy-ით თავიდან უშვებს
Readinessმზადაა თუ არა ტრაფიკისთვისPod გამოდის Service-ის endpoints-იდან (READY 0/1); არ რესტარტდება
Livenessცოცხალია თუ არა, ხომ არ „გაიჭედა“kubelet კონტეინერს რესტარტავს; RESTARTS იზრდება

პარამეტრები: periodSeconds — სიხშირე; timeoutSeconds — პასუხის ლოდინი; failureThreshold — რამდენი ზედიზედ წარუმატებლობა ითვლება ჩავარდნად.

startupProbe:
  httpGet: {path: /, port: 80}
  periodSeconds: 5
  failureThreshold: 12
  timeoutSeconds: 2
readinessProbe:
  httpGet: {path: /, port: 80}
  periodSeconds: 5
  failureThreshold: 3
  timeoutSeconds: 2
livenessProbe:
  httpGet: {path: /, port: 80}
  periodSeconds: 10
  failureThreshold: 3
  timeoutSeconds: 2

ჩავარდნის ცდა: liveness path /wrong-health-ზე → nginx 404 → probe ვარდება → ~30 წამში (3 × 10 წმ) კონტეინერი გადაიტვირთება და RESTARTS გაიზრდება. ჩანს kubectl describe pod-ის Events-ში (Liveness probe failed) და kubectl get pods -w-ით.

6საცავი: PV, PVC, StorageClass

კონტეინერის ფაილური სისტემა დროებითია: Pod-ის წაშლისას მონაცემი ქრება. მუდმივი მონაცემისთვის სამი ობიექტია.

ობიექტირა არისNamespace
PersistentVolume (PV)რეალური საცავის ნაწილი (დისკი, local დირექტორია, EBS); ადმინი ქმნის ან ავტომატურად იქმნებაარა, კლასტერის დონის
PersistentVolumeClaim (PVC)Pod-ის მოთხოვნა საცავზე: ზომა და access modeკი
StorageClassსაცავის კლასი: ვინ ქმნის PV-ს და როდის ხდება მიბმაარა

PVC ეძებს შესაფერის PV-ს და Bound ხდება. შემოწმება: kubectl get pv,pvc -n quiz2.

  • Access modes: ReadWriteOnce (RWO) — read-write ერთ node-ზე; ReadOnlyMany; ReadWriteMany; ReadWriteOncePod.
  • Reclaim policy: Retain — PVC-ის წაშლის შემდეგ PV და მონაცემი რჩება (Released), ადმინი ხელით ასუფთავებს; Delete — იშლება.
  • kubernetes.io/no-provisioner — დინამიკური შექმნა არ ხდება; PV ხელით (სტატიკურად) იქმნება.
  • volumeBindingMode: WaitForFirstConsumer — მიბმა ჩერდება, სანამ PVC-ის Pod არ დაიგეგმება; scheduler PV-ის node affinity-ს ითვალისწინებს. local საცავისთვის აუცილებელია.

Local PersistentVolume

Local PV კონკრეტული node-ის დირექტორიაა (მაგ. /var/lib/quiz2-data quiz2-worker-1-ზე), ამიტომ სჭირდება nodeAffinity node-ის kubernetes.io/hostname label-ით.

nodeAffinity:
  required:
    nodeSelectorTerms:
    - matchExpressions:
      - key: kubernetes.io/hostname
        operator: In
        values: [quiz2-worker-1]

Local საცავი HA გადაწყვეტა არ არის: node თუ დაიკარგა, მონაცემიც დაიკარგება.

მონაცემის შენარჩუნების დემონსტრაცია

  1. StatefulSet volumeClaimTemplates-იდან ქმნის PVC-ს quiz2-data-quiz2-stateful-app-0.
  2. PVC უერთდება quiz2-pv-ს; Pod საცავს /data-ზე ამაგრებს.
  3. ფაილის ჩაწერა: kubectl exec -n quiz2 quiz2-stateful-app-0 -- sh -c 'echo "Quiz 2 - Persistent Storage Works" > /data/student.txt'
  4. შლი მხოლოდ Pod-ს: kubectl delete pod quiz2-stateful-app-0 -n quiz2
  5. იგივე სახელის Pod იგივე PVC-ს უერთდება; cat /data/student.txt იგივე ტექსტს აჩვენებს.

7სქედულინგი: Labels, Taints, Tolerations

Labels და Selectors

Label key/value წყვილია ობიექტზე (Pod, Node, Service), მაგ. app=quiz2-web. Selector label-ებით ირჩევს ობიექტებს: Deployment — თავის Pod-ებს, Service — ტრაფიკის მიმღებ Pod-ებს. selector და label თუ არ ემთხვევა, Service-ს endpoints არ ექნება. ნახვა: kubectl get pods --show-labels.

Worker role label: kubectl label node rke2-worker-1 node-role.kubernetes.io/worker=worker — ამის შემდეგ ROLES სვეტში worker ჩანს. ROLES label-ებიდან გამოითვლება, ამიტომ <none> ნორმალურია და გაფუჭებას არ ნიშნავს. label მხოლოდ აღწერითია: დაგეგმვას თავისით არც კრძალავს, არც აიძულებს.

Taints და Tolerations

Taint node-ზე ედება და Pod-ებს „აგერიებს“; Pod მხოლოდ შესაბამისი toleration-ით დაიგეგმება.

Server-ის ინსტალაცია (master)

  1. curl -fsSL https://get.rke2.io -o install.sh — -f HTTP შეცდომაზე ჩავარდნა, -s ჩუმი, -S შეცდომის ჩვენება, -L redirect, -o ფაილში.
  2. sudo env INSTALL_RKE2_VERSION='v1.37.1+rke2r1' INSTALL_RKE2_TYPE=server sh install.sh
  3. /etc/rancher/rke2/config.yaml: node-name, node-ip (private IP), tls-san (IP API სერტიფიკატში), cni: canal.
  4. sudo systemctl enable rke2-server (boot-ზე) და sudo systemctl start rke2-server (ახლა).
  5. ლოგები: sudo journalctl -u rke2-server -f
  6. kubeconfig: /etc/rancher/rke2/rke2.yaml → ~/.kube/config, chmod 600; PATH-ში /var/lib/rancher/rke2/bin.
  7. Join token: sudo cat /var/lib/rancher/rke2/server/node-token — ძალიან მგრძნობიარეა.

Agent-ის ინსტალაცია (worker)

  1. იგივე ინსტალერი, იგივე ვერსია, INSTALL_RKE2_TYPE=agent.
  2. config.yaml: server: https://<MASTER_PRIVATE_IP>:9345, token, უნიკალური node-name და node-ip; ფაილს chmod 600.
  3. systemctl enable + start rke2-agent; პრობლემისას journalctl -u rke2-agent -n 50 --no-pager.
  4. master-ზე: kubectl get nodes -o wide — სამივე Ready.
  5. შემდეგ worker role label-ები და master-ის NoSchedule taint (სექცია 7).

საკუთარი image

Dockerfile: FROM nginx:stable-alpine, COPY index.html /usr/share/nginx/html/index.html, EXPOSE 80. EXPOSE მხოლოდ მეტამონაცემია და ჰოსტის პორტს არ ხსნის. შემდეგ docker build -t USER/rke2-demo:v1 . (წერტილი = მიმდინარე დირექტორია), docker login, docker push; worker-ები image-ს registry-დან იწერენ.

Production-ისთვის

  • ერთი master = single point of failure. HA: ჩვეულებრივ 3 RKE2 Server, etcd quorum, სტაბილური API endpoint.
  • etcd snapshot-ების და token-ის უსაფრთხო backup, აღდგენის ტესტი.
  • ვერსიების pin და დაგეგმილი განახლება.
  • EBS volume-ებს სჭირდება CSI driver და IAM; LoadBalancer-ს — AWS cloud controller.
  • Least-privilege IAM, RBAC, NetworkPolicy, TLS, მონიტორინგი, ლოგირება, dev/test/prod გამიჯვნა.

Local Linux სერვერებზე იგივე პროცესია; Security Group-ის ნაცვლად LAN/DNS მარშრუტიზაცია და ჰოსტის firewall.
